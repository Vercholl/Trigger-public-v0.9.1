# Информационная безопасность trigger

Документ описывает механизмы защиты панели и чек-лист развёртывания на сервере
компании. Аудит проведён 28.10, ужесточён 05.11 (v0.8.6 — требования ИБ:
история паролей, idle-сессии, лимиты тел, панель самодиагностики). Все
перечисленные механизмы реализованы в коде.

## 1. Аутентификация и сессии

- **Пароли**: bcrypt (cost 12). Политика (v0.8.6): ≥ 10 символов
  (env `PASSWORD_MIN_LENGTH`, 8..128), буквы + цифры; не email/имя владельца;
  не из локального блэклиста популярных (qwerty/пароль/…); нельзя повторить
  текущий и один из 5 последних (`PasswordHistory`, bcrypt-хеши). Политика
  применяется только при установке НОВОГО пароля — существующие пароли не
  ретроактивны. Первый вход под стартовым админом — принудительная смена
  (`mustChangePassword`).
- **Сессии**: токен = 32 случайных байта; в БД хранится только sha256(токен).
  Cookie `tg_sid` — `HttpOnly` (недоступен JS), `SameSite=Lax` (или
  `None; Secure; Partitioned` при HTTPS за шлюзом). Абсолютный TTL 30 дней
  (`SESSION_TTL_HOURS`) **+ idle-таймаут 7 дней без активности**
  (`SESSION_IDLE_HOURS`, 0 = выключен; v0.8.6): активность продлевает окно
  (touch не чаще 1 раза в 5 мин на сессию — без записи в БД на каждый запрос),
  давно неактивные сессии чистятся и при обращении, и воркером. Угнанная/
  заброшенная сессия живёт максимум 7 дней без запросов.
- **Самообслуживание сессий**: раздел «Настройки» → «Безопасность» — список СВОИХ активных
  сессий (устройство, IP, активность), завершение любой своей (кроме текущей —
  для неё «Выйти») и «Завершить все прочие»; действия аудируются
  SESSION_REVOKED. Идентификатор сессии наружу — sha256-хеш токена (по нему
  токен не восстановить), удаление — только владельцем (where userId+idHash).
- **Брутфорс**: 30 попыток входа / 5 мин с одного IP (429) + блокировка
  аккаунта на 15 минут после 5 неудачных попыток (423, счётчик атомарным
  инкрементом; срабатывание фиксируется отдельной записью LOGIN_LOCKED).
  Подбор СТАРОГО пароля при смене (украденная сессия) — лимит 10 попыток /
  10 мин на пользователя (429).
- **Анти-перечисление email**: ответ на неверный email и неверный пароль
  одинаковый; при отсутствии пользователя выполняется фиктивная bcrypt-проверка
  (выравнивание времени ответа). Деактивация аккаунта проверяется ПОСЛЕ сверки
  пароля: неверный пароль на деактивированном аккаунте неотличим от неизвестного
  email (единый 401); блокировка (423) тоже отдаётся после фиктивной bcrypt —
  тайминг не выдаёт заблокированные аккаунты.
- **Смена пароля** инвалидирует все другие сессии пользователя и записывает
  прежний пароль в историю (вернуть старый нельзя).
- Bearer-фолбэк (`Authorization: Bearer`) — только для сред, где браузер
  блокирует cookie (кросс-сайт iframe предпросмотра). Токен в localStorage
  не хранится, если работает cookie-сессия.

## 2. Авторизация (RBAC)

| Область | VIEWER | MANAGER | ADMIN |
|---|---|---|---|
| Чтение (клиенты, шаблоны, воронки, рассылки, SMS-лог, события, отписки, ссылки, настройки, реестр кастомных полей, история профиля, журнал операций массового обновления, сводка «радара») | ✔ | ✔ | ✔ |
| Запись домена (создать/изменить/запустить; операции массового обновления профилей — создание/отмена) | ✖ (403) | ✔ | ✔ |
| Пользователи, API-ключи, журнал аудита | ✖ | ✖ | ✔ |
| Настройки (запись), интеграции/креды провайдеров, «Захват событий» (тумблер/токен), реестр кастомных полей (создание/правка/деактивация/безвозвратное удаление), удаление наблюдений «радара» | ✖ | ✖ | ✔ |
| Скачивание дистрибутива (архив = серверный код) | ✖ | ✖ | ✔ |

Проверка выполняется единой обёрткой `withAuth` на каждом route-handler'е;
роль берётся из сессии (не из запроса). VIEWER получает 403 на любой не-GET.
Фронтовая блокировка действий (ViewerGuard) реализована атрибутом `inert`
на обёртке — гасит клики, фокус и клавиатуру для поддерева любого вида
(раньше `disabled` через cloneElement работал только на кнопках); это UX,
первичная защита — серверная.

## 3. CSRF / кросс-сайтовые запросы

Все мутирующие запросы (включая auth-роуты) проходят гейт `checkSameOrigin`:

1. `Sec-Fetch-Site` (ставит браузер, не подделывается): `cross-site` → 403;
2. легаси-фолбэк — сверка имени хоста `Origin` с `Host`/`X-Forwarded-Host`
   (порты игнорируются: шлюзы их переписывают);
3. запросы с `Authorization: Bearer` (не-браузерные клиенты) гейтом не
   блокируются — их защищает сам токен.

Плюс SameSite-cookie и отсутствие CORS-заголовков (API доступен только
same-origin; междоменные браузерные вызовы невозможны).

## 4. Публичные эндпоинты (вне сессии)

| Эндпоинт | Защита |
|---|---|
| `POST /api/v1/hooks/events` | токен приёмника (Bearer или `?token=`), timing-safe сверка; тумблер; батч ≤ 5000; тело ≤ 5 МБ (413); rate-limit 300/мин с IP (до чтения настроек) |
| `POST /api/v1/events` | `X-Api-Key` (статический env или ключ из БД: sha256 + IP-allowlist + отзыв), тело ≤ 2 МБ (413), rate-limit 120/мин |
| `POST /api/v1/webhooks/smstech` | секрет `SMSTECH_WEBHOOK_SECRET` в Authorization (опционально, константное время), тело ≤ 2 МБ, rate-limit 300/мин |
| `GET /api/v1/webhooks/t2` | `?secret=T2_WEBHOOK_SECRET` (опционально, константное время), rate-limit 300/мин |
| `POST /api/v1/webhooks/mts` | `?secret=MTS_WEBHOOK_SECRET` (опционально, константное время; в протоколе МТС V.1.14 подписи коллбэков нет), items ≤ 1000, тело ≤ 2 МБ, rate-limit 300/мин |
| `POST /api/v1/webhooks/smsru` | MD5-hash подписи (алгоритм ПРОВЕРИТЬ ПО ДОКУМЕНТАЦИИ SMS.RU — адаптер «спящий», провайдер в реестр не подключён; при пустых env — 503), тело ≤ 2 МБ, rate-limit 300/мин |
| `GET/POST /api/v1/unsubscribe`, `/api/v1/u`, `GET /r` | HMAC-токен/код ссылки, rate-limit 60/мин, маскированный номер, без перечисления |

**Лимиты тел (v0.8.6)**: все публичные приёмники ограничивают размер тела
двухуровнево — ранний отбой 413 по `Content-Length` (до чтения тела) и контроль
фактической длины после чтения (обход через chunked/ложный Content-Length не
работает). «Толстый» POST не монополизирует память/ЦП на парсинге.
Неудачные аутентификации на приёмниках (неверный токен/ключ/секрет) фиксируются
записями SECURITY в аудите с троттлингом 1 запись / 10 мин на (вид, IP) —
молотилка не раздувает журнал, факт и адрес атаки видны.

Рекомендация для продакшена: **задать** `SMSTECH_WEBHOOK_SECRET`,
`T2_WEBHOOK_SECRET` и `MTS_WEBHOOK_SECRET` — тогда webhook-ы подписаны.
Rate-limit на вебхуки
(300/мин с IP) отсекает молотилку по идентификаторам и подбор секрета.

## 5. Секреты

- В БД секреты провайдеров (токен SMS.Tech, логин/пароль Т2 и МТС
  OmniChannel) хранятся зашифрованными AES-256-GCM (ключ — `SECRETS_KEY`
  в env, scrypt). Утечка копии БД не раскрывает креды.
- В панель секреты **не возвращаются** ни в каком виде — только маски
  (`••••••••9f2c`).
- `.env` не попадает в git/дистрибутив; права `chmod 600`.
- Токены в логах: приёмник событий предпочитает `Authorization: Bearer`
  (`?token=` — только для совместимости с настроенным отправителем).
- Статический `EVENTS_API_KEY` сверяется за постоянное время.

## 6. Валидация и инъекции

- Все тела запросов — zod-схемы; мусор → 400/422 (ProblemDetails RFC 7807,
  без стеков и внутренностей).
- Prisma ORM — параметризованные запросы; raw-SQL в коде один (`SELECT 1`).
- CSV-импорт: кап 2 МБ, построчная валидация типов.
- Пагинация: `pageSize` ≤ 100 (защита от вытягивания всей базы одним запросом).
- Open redirect: `/r` редиректит только на `http(s)://`-URL из БД (создаётся
  MANAGER+ и валидируется при создании); параметры запроса адрес не задают.
- XSS: React-экранирование; `dangerouslySetInnerHTML` в домене нет.
- Экспорт CSV — с аудитом (кто/когда/фильтры).

## 7. HTTP-заголовки безопасности

Включаются в `next.config.ts` (production-режим — полный набор):

- `X-Content-Type-Options: nosniff`;
- `Referrer-Policy: strict-origin-when-cross-origin`;
- `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`;
- `Strict-Transport-Security: max-age=15552000` (полгода; на http браузеры
  игнорируют);
- `Content-Security-Policy`: всё только с себя (`default-src 'self'`,
  `connect-src 'self'` — блокирует эксфильтрацию на внешние домены при XSS;
  inline-стили/скрипты Next.js разрешены);
- `/api/*` — `Cache-Control: no-store` (авторизованные ответы не кэшируются
  посредниками);
- `FRAME_PROTECTION=1` (env) → `X-Frame-Options: DENY` на каждом ответе
  (runtime-проверка в `src/proxy.ts` — работает и с готовым архивом, без
  пересборки). При сборке с этим же env — дополнительно `frame-ancestors
  'none'` в CSP. **Включайте на сервере компании**, если панель не
  встраивается в другие системы (по умолчанию выключено, чтобы не ломать
  предпросмотр платформы).

## 8. Аудит и самодиагностика

Все значимые действия пишутся в `audit_logs`: входы (успех/провал, с
User-Agent), **срабатывание брутфорс-лока (LOGIN_LOCKED — отдельной строкой)**,
выходы, **отзыв сессий (SESSION_REVOKED)**, CRUD клиентов/шаблонов/воронок/
сегментов/рассылок, импорт, экспорт CSV, изменения настроек и секретов,
отписки, CRUD кастомных полей (вкл. деактивацию), операции массового
обновления (создание/отмена), удаление наблюдений «радара» — с пользователем,
IP и деталями.
**SECURITY-события (v0.8.6)**: неудачные аутентификации на публичных
приёмниках (неверный токен/ключ/секрет webhook-а) и подбор старого пароля при
смене — троттлинг 1 запись / 10 мин на (вид, IP) для приёмников (молотилка не
раздувает журнал), по записи на попытку для смены пароля (лимит 10/10 мин).
Чтение журнала — только ADMIN. Запись аудита не ломает основной сценарий.

**Панель «Состояние защиты» (v0.8.6, раздел «Настройки» → «Безопасность», ADMIN)**:
GET `/api/v1/security/status` — живой чек-лист конфигурации для отдела ИБ:
дефолтный админ-пароль сменён, секреты env заданы (SESSION/SECRETS/
UNSUBSCRIBE), ключи приёма (БД/env), подписи webhook-ов, токен приёмника,
креды провайдеров в БД зашифрованы, production-режим, FRAME_PROTECTION,
idle-таймаут, пользователи с несменённым паролем, индикатор атак (неудачные
входы за 24 ч, блокировки) + счётчики (сессии/ключи/аудит) и активная политика
(длина/история паролей, TTL/idle сессий, лимиты). Красный пункт = конкретная
дыра с рекомендацией, жёлтый = осознанный компромисс окружения. Секреты не
раскрываются — только факты «задан/не задан».

**Самообслуживание сессий (v0.8.6, все роли)**: GET/DELETE
`/api/v1/auth/sessions` (+ `/{id}`) — список своих сессий, завершение любой
своей/всех прочих с аудитом SESSION_REVOKED.

## 9. Хранение и резервирование данных

- SQLite-файл `db/custom.db` — перс. данные клиентов (телефоны, ФИО, суммы).
  Доступ к файлу на сервере — только владелец процесса; бэкапы — в защищённый
  каталог.
- В дистрибутив БД не попадает; снапшоты — вне web-root (не раздаются
  статикой).
- Воркер делает периодический снапшот БД (канал сохранности; `db-backup.ts`).
- **Архив ретеншна журнала доставки** (Task 63): `db/message-events-archive/`
  — JSONL/gz-файлы, в которые выгружаются события MessageEvent ПЕРЕД
  удалением по окну «Хранить журнал событий доставки, дней». Содержат те же
  перс. данные (телефоны), что и журнал: права на каталог — как на БД
  (владелец процесса, вне web-root); вывоз/хранение — по тому же регламенту,
  что и снапшоты БД. Отключается значением 0 (не удалять — архив не растёт).

## 10. Чек-лист развёртывания на сервере компании

1. `cp .env.example .env && chmod 600 .env`; заполнить ВСЕ секции
   `openssl rand` (SESSION_SECRET, UNSUBSCRIBE_SECRET, SECRETS_KEY,
   EVENTS_API_KEY, ADMIN_PASSWORD) — дефолтов/плейсхолдеров не оставлять.
2. `ADMIN_PASSWORD` — стойкий; первый вход потребует смену.
3. Заполнить `SMSTECH_WEBHOOK_SECRET` / `T2_WEBHOOK_SECRET` /
   `MTS_WEBHOOK_SECRET` и сообщить значения провайдерам (подписанные webhook-и).
4. Установить `FRAME_PROTECTION=1` (если панель не встраивается в iframe).
5. TLS: терминировать HTTPS на корпоративном reverse-proxy (nginx/и т.п.),
   пробрасывать на порт приложения; HSTS приложение выставляет само.
6. Боевой доступ — ЧЕРЕЗ reverse-proxy, ставящий `x-real-ip` (nginx:
   `proxy_set_header X-Real-IP $remote_addr;`) — IP нужен rate-лимитам и аудиту.
   При прямом доступе (без прокси/заголовка) rate-лимиты делят общий бакет
   `direct` — 30 попыток/5 мин на ВСЕХ клиентов (легитимные пользователи
   блокируют друг друга), а аудит пишет `ip=direct` без адреса.
7. Ограничить сетевой доступ: панель — только сотрудникам (VPN/корп. сеть),
   публичные эндпоинты (`/api/v1/hooks/*`, `/api/v1/events`,
   `/api/v1/webhooks/*`, `/api/v1/u`, `/api/v1/unsubscribe`, `/r`) — открыть
   источникам событий и шлюзам провайдеров.
8. API-ключи приёма событий заводить через «Интеграции» → «Интеграция с
   системой данных» → блок «API-ключи» с IP-allowlist адресов системы данных;
   статический `EVENTS_API_KEY` заменить на ключ из БД.
9. Файл БД и каталог бэкапов — вне каталогов, отдаваемых веб-сервером.
10. Регламент: смена паролей сотрудников (политика ≥ 10 симв. и анти-повтор —
   на сервере), просмотр журнала аудита (в т.ч. SECURITY/LOGIN_LOCKED),
   периодическая проверка раздела «Безопасность → Состояние защиты»,
   тестовое восстановление из бэкапа.
11. Обновления — пакетом дистрибутива (`deploy/update.sh`), контроль SHA-256.
12. Настроить по политике компании: `SESSION_TTL_HOURS` / `SESSION_IDLE_HOURS`
    (жёстче дефолтов 720/168 ч) и `PASSWORD_MIN_LENGTH` (если норма выше 10).

## 11. Известные ограничения (осознанные решения)

- **Webhook-подписи зависят от провайдеров**: SMS.Tech, Т2 и МТС OmniChannel
  не предусматривают
  цифровой подписи тела (только общий секрет в заголовке/URL) — это лимит их
  протоколов. При заданном секрете подделка исключена, без секрета — webhook
  принимает только ретрансляцию статусов существующих сообщений (не создаёт
  новых данных) и ограничен 300 req/мин; коллбэк МТС дополнительно — 1000
  элементов items за запрос (413 сверх; каждый элемент = 2–4 обращения к БД).
  Для активного МТС в продакшене секрет СЛЕДУЕТ задать всегда — карточка МТС
  на подкладке «SMS-провайдеры» раздела «Интеграции» предупреждает, когда
  MTS_WEBHOOK_SECRET пуст.
- **CSP с 'unsafe-inline'/'unsafe-eval'** для скриптов: Next.js инжектит
  бутстрап без nonce. Усиление (nonce-планирование) — при доработке фронтенда.
- **Bearer-фолбэк в localStorage** включается только если браузер блокирует
  cookie (iframe предпросмотра). При обычном развёртывании токен не хранится.
  Взаимоисключающие режимы: `FRAME_PROTECTION=1` (X-Frame-Options: DENY на
  каждый ответ) ломает встроенный iframe-предпросмотр — включать только если
  панель НЕ встраивается в чужие страницы (чек-лист §10, п. 4).
- Rate-limiter на SQLite — один экземпляр приложения; при масштабировании на
  несколько инстансов заменить на Redis.
- **История паролей и touch сессий — per-instance**: in-memory троттлинг
  (touch 5 мин, SECURITY 10 мин) обнуляется при рестарте — это только
  разрежение записи, корректность не зависит от него (проверки — в БД).
- CSV-импорт не поддерживает кавычки RFC 4180: значения с разделителем
  (`,`/`;`) внутри ячейки дают ошибку строки — она видна в сводке импорта,
  остальные строки импортируются.
