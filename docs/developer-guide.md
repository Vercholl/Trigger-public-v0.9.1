# Руководство разработчика — карта кодовой базы trigger

Этот документ — отправная точка для программистов, которые будут разбираться в
проекте, чинить его или вносить доработки после развёртывания на серверах
компании. Каждый файл исходного кода снабжён русскими комментариями (заголовок
файла + JSDoc на экспортах + пояснения неочевидной логики); здесь — общая карта,
которая подскажет, в какой каталог смотреть в каждой ситуации.

Смежные документы: `README.md` (продуктовый обзор и quick start),
`docs/api-contract.md` (полный контракт REST API), `docs/security.md`
(аудит безопасности и чек-лист развёртывания), `docs/loadtest-report.md`
(нагрузочный отчёт: 4 млн клиентов / 500 тыс. SMS в месяц), `SPEC.md`
(мастер-документ с решениями и допущениями), `.env.example` (все переменные
окружения с комментариями).

## 1. Технологический стек

| Слой | Технология |
|---|---|
| Фреймворк | Next.js 16 (App Router), режим standalone |
| Язык | TypeScript 5 (strict) |
| БД | SQLite + Prisma ORM (клиент `@prisma/client`) |
| UI | React 19, Tailwind CSS 4, shadcn/ui (New York), Lucide-иконки, Recharts (графики) |
| Состояние | Zustand — навигация/сессия на клиенте; TanStack Query — серверные данные |
| Валидация | Zod (схемы в сервисах, рядом с бизнес-логикой) |
| Пароли/секреты | bcryptjs (cost 12); AES-256-GCM для секретов интеграций (`enc:v1:`) |
| Рантайм | Bun (dev/скрипты); production — Node (`node .next/standalone/server.js`) |

Файл `db/custom.db` — единственная база (SQLite). Схема описана в
`prisma/schema.prisma` и снабжена комментариями к каждой таблице.

## 2. Как поднять проект локально

```bash
cp .env.example .env     # заполнить секреты (каждая переменная прокомментирована)
bun install
bun run db:push          # применить схему к db/custom.db
bun run db:seed          # (только dev) синтетические демо-данные
bun run dev              # http://localhost:3000, лог — dev.log
```

Вход: `ADMIN_EMAIL` / `ADMIN_PASSWORD` из `.env`. Проверка живости:
`curl http://localhost:3000/api/health` → `{"status":"ok","db":"ok",...}`.

Проверки качества: `bun run lint` (ESLint), `bunx tsc --noEmit` (типы).
Больше никаких тестов в проекте нет — регресс проверяется вручную по
`scripts/e2e-broadcast-test.ts` и живой песочницей.

Нагрузочный стенд (как воспроизвести замеры из `docs/loadtest-report.md`):
`bun scripts/loadtest-seed.ts` — синтетическая база боевого масштаба
(4 млн клиентов / 2 млн SMS / 4,4 ГБ; требует КОПИЮ рабочей БД — таблицы
должны уже существовать, боевые данные не тронуты), затем
`bun scripts/loadtest-bench.ts` — бенчмарк РЕАЛЬНЫХ сервисных функций
(чтение/воркер/запись) с отчётом в `/tmp/trigger-loadtest/`. Запускать на копии,
не на рабочей БД.

Демо-данные: базовый объём сеет `prisma/seed.ts` (bun run db:seed);
«жирную» демо-базу собирает `scripts/expand-demo-data.ts`
(`bun scripts/expand-demo-data.ts [фактор]`, по умолчанию ×20 — клиенты/SMS/
события/переходы; там же — кейс «Кредитная линия»: реестр кастомных
полей is_credit_line / available_tranche_sum / grace_period_days со значениями,
историей профиля и демо-операцией массового обновления). Регламент: расширение
демо-данных — только синтетикой (152-ФЗ), скрипты запускаются вручную
и не входят в production-инструкцию.

## 3. Архитектура: модульный монолит, четыре слоя

```
┌──────────────────────────────────────────────────────────────────────┐
│  БРАУЗЕР (SPA на единственном роуте /)                               │
│  page.tsx → AppShell (сайдбар) → views/* (экраны)                    │
│  Навигация: Zustand-стор store.ts (?view=…), данные: TanStack Query  │
│  через api-client.ts (cookie tg_sid + Bearer-фолбэк)                │
└───────────────────────────┬──────────────────────────────────────────┘
                            │  fetch /api/v1/**  (JSON, problem+json)
┌───────────────────────────▼──────────────────────────────────────────┐
│  API-СЛОЙ  src/app/api/**                                           │
│  Тонкие роуты: withAuth (RBAC) → Zod-валидация → вызов сервиса      │
│  Единый формат ошибок RFC 7807 — см. src/lib/api.ts                 │
└───────────────────────────┬──────────────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────────────┐
│  СЕРВИСЫ  src/lib/services/*                                        │
│  ВСЯ бизнес-логика: клиенты, шаблоны, воронки, рассылки, сегменты,  │
│  аудит, RBAC-гварды, Zod-схемы. Работают с Prisma (db)              │
└───────────────────────────┬──────────────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────────────┐
│  ИНФРАСТРУКТУРА  src/lib/*                                          │
│  engine/   — движок воронок (интерпретатор узлов)                   │
│  scheduler/worker.ts — фоновый воркер (тики каждые ~5 с)            │
│  provider/ — адаптеры SMS-провайдеров (smstech / t2 / mts / sandbox)│
│  compliance/ — юр-проверки перед отправкой (152-ФЗ, реклама, отписка)│
│  registry/ — реестры полей: карточка клиента + cf_-пространство имён │
│  security/  — сессии, пароли, API-ключи, аудит, rate-limit          │
│  sms/       — сегментация (160/70 символов) и рендер шаблонов       │
│  db.ts + db-bootstrap.ts — подключение и самобутстрап БД            │
└──────────────────────────────────────────────────────────────────────┘
```

Воркер запускается через `src/instrumentation.ts` (Next.js-хук старта сервера):
восстановление снапшота → бутстрап БД → `startWorker()`. Он же делает
периодический бэкап БД. Приложение поднимается даже на пустом сервере — схема
и стартовый админ создаются автоматически.

## 5. Поток типового HTTP-запроса

Пример: пользователь сохраняет шаблон.

1. **Фронтенд**: `templates-view.tsx` → мутация TanStack Query → `api-client.ts`
   (`PUT /api/v1/templates/{id}`, JSON) → cookie `tg_sid` прикладывается
   автоматически.
2. **Роут** `src/app/api/v1/templates/[id]/route.ts` (3–5 строк кода):
   оборачивает обработчик в `withAuth(..., { write: 'MANAGER' })`, читает тело
   `readJson`, дергает сервис.
3. **`withAuth`** (`src/lib/api.ts`): достаёт сессию из cookie/Bearer →
   проверяет роль → прокидывает `user` в обработчик. Роли: VIEWER < MANAGER <
   ADMIN; не-GET по умолчанию требует MANAGER, GET — любую роль.
4. **Сервис** `src/lib/services/templates.ts`: Zod-схема `.parse()` (ошибка →
   422), бизнес-гварды (409 если шаблон занят активной воронкой), запись в
   Prisma, `logAudit(...)` — кто/что/когда/с какого IP.
5. **Ответ**: успех — JSON роут возвращает сам; ошибки — единый
   problem+json `{type,title,status,detail}` (маппинг в `lib/api.ts`).

Чтобы найти, кто вызовет ваш новый код: `grep -r "имя-функции" src/`.

## 6. Жизненный цикл триггерной рассылки (главный поток)

```
Система данных ──POST /api/v1/events (X-Api-Key)──► events_inbox (NEW)
                                                         │
                             ┌── каждые ~5 c ────────────▼──────────┐
                             │  scheduler/worker.ts (тик)           │
                             │  1) claim события (атомарно)         │
                             │  2) upsert карточки клиента + cf_    │
                             │  3) для каждой активной воронки       │
                             │     с этим triggerEvent:              │
                             │     engine.startInstance()            │
                             └───────────────┬───────────────────────┘
                                             ▼
                    engine.ts: цикл по узлам воронки (continueInstance)
                    ├── condition → expression.ts (безопасный мини-язык)
                    ├── delay     → scheduled_jobs (run_at) → ждёт тика
                    ├── waitEvent → «спит» до события или таймаута
                    ├── sms       → compliance/pipeline.ts (юр-проверки)
                    │              → sms/render.ts ({{переменные}})
                    │              → sms/segments.ts (части SMS)
                    │              → provider/send → sms_messages (лог)
                    └── end       → статус экземпляра COMPLETED
```

Идемпотентность везде: события — по `idempotency_key`, задачи — claim-стиль,
отправки у провайдеров — по детерминированному `idempotency_key`. Воркер
переживает рестарт сервера: невыполненное подхватывается из `scheduled_jobs`.

Статусы доставки приходят отдельно (см. раздел 8) и доводят `sms_messages`
до финального состояния (DELIVERED / FAILED). Каждое сообщение дополнительно
фиксирует `varsSnapshot` — снимок переменных, реально использованных шаблоном,
на момент рендера (P6): в SMS-логе и карточке клиента видно, что именно
подставилось, без восстановления состояния профиля на дату отправки.

## 8. Захват событий доставки (статусы от провайдера)

Два независимых канала, дублирующие друг друга (на случай отказа одного):

1. **Webhook-приёмник** `POST /api/v1/hooks/events`: токен из настроек
   (константа-сравнение), лимит тела, идемпотентность по `dedupKey`
   (unique-индекс в `MessageEvent`), сырой payload сохраняется целиком.
2. **Опрос провайдера** воркером: `status()` адаптера по незакрытым сообщениям.

Оба канала сходятся в `services/message-events.ts → applyExtEvent()`: машина
состояний доводит `sms_messages` (send/deliv/unsub), тарификация и оператор
дописываются в лог. Тумблер включения и ротация токена — «Интеграции» →
подкладка «Интеграция с системой данных» → карточка «Захват событий». Синонимы
статусов разных провайдеров нормализуются там же.

## 9. Комплаенс (юридические проверки перед отправкой)

`src/lib/compliance/pipeline.ts` — единая точка: перед КАЖДОЙ отправкой
проверяет стоп-лист (UNSUBSCRIBED — только для рекламы), согласие
(`sms_consent`), рекламную приписку (`disclaimer.ts` — шаблон
«Реклама. {advertiser}. Отписаться: {link}»), тихие часы (`quiet-hours.ts` —
окно по умолчанию 21:00–09:00 в TZ клиента), лимиты (3/сутки клиенту,
5000/сутки системе). Сервисные SMS (напоминания о платежах) проходят без рекламных
проверок — доставка всегда. Короткие персональные ссылки отписки
(`short-links.ts`, код из 7 символов, срок 180 дней) и маркетинговые ссылки
с UTM (`marketing-links.ts`) — там же.

## 10. Рецепты «как добавить…»

### 10.1 Новый API-эндпоинт

1. Создать `src/app/api/v1/<домен>/route.ts` по образцу соседних:
   заголовок-комментарий (метод/путь/RBAC/коды ответов), `withAuth`,
   `readJson` + Zod-схема из сервиса.
2. Логику — в соответствующий `src/lib/services/*.ts` (или новый сервис).
3. Гварды возвращают `NextResponse.json({type:'about:blank', title, status},
   {status})`; Zod-ошибку достаточно бросить — `withAuth` сам отдаст 422.
4. Значимые изменения — `logAudit()` из `security/audit.ts`.
5. Контракт обновить в `docs/api-contract.md`.

### 10.2 Поле или таблица в БД

1. Править `prisma/schema.prisma` (SQLite: без enum, списки — JSON-строки).
2. `bun run db:push` (dev) — применить; `bun run db:generate` — клиент.
3. **ВАЖНО для боевого сервера**: перегенерировать DDL-бутстрап:
   `bun scripts/gen-bootstrap-ddl.ts` (встроен в `db-bootstrap.ts`, применяет
   схему на чистом сервере при старте). Проверить в свежем дистрибутиве.
4. Для существующих боевых БД — миграция `bun run db:migrate` либо ручной SQL.

### 10.3 Новый экран панели

1. Добавить идентификатор в `View` и `VIEWS` (`src/lib/store.ts`).
2. Создать `src/components/views/<домен>-view.tsx` (по образцу соседних:
   TanStack Query + shared.tsx-компоненты; пишущая роль — за ViewerGuard).
3. Зарегистрировать в `app-shell.tsx`: массив `NAV` (сайдбар, иконка, роли) и
   `ViewSwitch` (рендер).
4. Файл `?view=<id>` в URL поддерживается автоматически (replaceState).

Альтернатива для «подразделов» — паттерн «раздел-поднавигация» (Task 58/59:
«Безопасность»/«Кастомные поля»/«Ссылки» живут вкладками раздела «Настройки»,
«Интеграция с системой данных»/«SMS-провайдеры» — вкладками раздела
«Интеграции»): значение view добавляется БЕЗ пункта сайдбара — включается
в `SETTINGS_SECTION_VIEWS` / `INTEGRATIONS_SECTION_VIEWS` (`app-shell.tsx`),
рендерится общим компонентом SettingsView/IntegrationsView с вкладками
(forceMount — черновики форм не теряются при переключении вкладок); пункт
сайдбара родительского раздела подсвечивается, `?view=<id>` остаётся рабочей
ссылкой.

### 10.4 Новый тип узла воронки

1. `engine/types.ts`: тип узла в `FunnelNode` + исходы в `NodeOutcome`.
2. `engine/executors.ts`: класс-исполнитель (НЕ меняет статус экземпляра сам —
   только возвращает исход CONTINUE/WAIT/FAIL; SMS-узлы проходят комплаенс).
3. `engine/validate.ts`: правила валидации графа для нового типа.
4. `services/funnels.ts`: Zod-схема узла.
5. `views/funnels-view.tsx`: карточка шага в конструкторе + преобразование
   `stepsFromDefinition` / `buildDefinition`.
6. Движок и БД расширения не требуют (реестр исполнителей).

### 10.5 Новый SMS-провайдер

1. По образцу `provider/smstech.ts` или `provider/mts.ts` реализовать
   интерфейс `SmsProvider` (`provider/types.ts`): `send()` (обязательно —
   детерминированный ключ идемпотентности для ретраев без дублей; у МТС это
   `message_id` — детерминированный UUID из sha256(idempotencyScope), НО
   платформа не гарантирует дедупликацию по нему — см. шапку `mts.ts`)
   и `status()`. Временные ошибки → `TemporaryProviderError` (ретрай с
   backoff), постоянные → `ok:false`. Креды — из БД с fallback на env
   (образец: `mtsCredentials()` с кэшем 30 с и инвалидацией после сохранения).
2. Зарегистрировать адаптер в `getProvider()` (`provider/types.ts`) и
   добавить имя в zod-enum `provider` в `services/settings.ts` (иначе
   активация из панели вернёт 422).
3. Экран «Интеграции» (`views/integrations-view.tsx` + `services/integrations.ts`):
   карточка подключения (PROVIDER_IDS + listIntegrations), хранение секретов —
   только `enc:v1:` (AES-256-GCM, `security/secrets.ts`); роуты
   `/integrations/<имя>/credentials|check|test` (ADMIN + rate-limit).
4. Webhook статусов (если есть) — роут `api/v1/webhooks/<имя>` + нормализация
   статусов в `message-events.ts` (source-union пополняется именем
   провайдера; маппинг кодов — единая функция, как `mapMtsStatus`).
5. Реконсиляция воркера: добавить имя в `provider: { in: [...] }` фильтра
   «зависших» SENT (`scheduler/worker.ts → reconcileDeliveryStatuses`).

### 10.6 Новое поле карточки клиента

Единый реестр — `src/lib/registry/card-fields.ts` (`FIELD_DEFS`): одно
описание поля (fieldName / prisma-колонка / тип / метка / категория / подсказка)
питает сериализацию API, CSV-колонки, конструктор сегментов
(`src/lib/segments/fields.ts` генерирует поля из реестра) и подсказки
шаблонов (`KNOWN_TEMPLATE_VARS` в `src/lib/sms-utils.ts`) — их править
НЕ нужно, дрейф описаний исключён.

1. `prisma/schema.prisma`: типизированная nullable-колонка в модели `Client`
   + индекс при необходимости (см. 10.2 — db:push и перегенерация DDL).
2. `src/lib/registry/card-fields.ts`: строка в `FIELD_DEFS`.
3. `src/lib/services/client-card.ts`: ключ в zod-схеме — сверка с реестром
   идёт НА КОМПИЛЯЦИИ (`satisfies`): лишнее/отсутствующее поле не соберётся.
4. Если поле уже сыплется от системы данных — оно видно в «радаре» неизвестных полей
   (журнал «События», сводка `/events/unknown-fields`); после подключения
   наблюдение можно убрать крестиком (новое упоминание воссоздаст его).

Если поле нужно «здесь и сейчас» без доработки кода и релиза — заведите
кастомное поле (10.7): оно живёт в реестре БД и принимается из `client_card`
автоматически.

### 10.7 Кастомное поле профиля (без доработки кода)

1. Раздел «Кастомные поля» (или `POST /api/v1/custom-fields`, ADMIN): ключ
   (`is_credit_line`), тип `text|number|date|bool`. Тип задаёт колонку
   хранения EAV-lite (`ClientFieldValue`) и операторы сегментации — после
   создания НЕ меняется. Деактивация (PATCH `isActive=false`) — обратимый
   путь: значения сохраняются, живые шаблоны не ломаются; удаление
   (DELETE `{id}`) — безвозвратное (поле + все значения), блокируется 409,
   пока переменной пользуются шаблоны/воронки/сегменты.
2. Значения: вручную в карточке клиента (`custom_fields` в POST/PUT
   `/clients`), из `client_card` событий (ключи `cf_<key>` / сырой `<key>` /
   camelCase контракта системы данных `isCreditLine` — применяются воркером до запуска
   воронок) или массовой операцией по сегменту
   (`POST /clients/mass-update`).
3. Потребление: переменная `{{cf_<key>}}` в шаблонах/воронках/рассылках,
   правило сегмента `cf_<key>` (SQL EXISTS по индексам), условие воронки
   `client.cf_<key>`. Код при этом не меняется вовсе.

- **Комментарии — на русском**; термины (cookie, Prisma, bcrypt) латиницей.

  shadcn/ui, её не комментируем и не правим.
- **Ошибки API — только problem+json** (`{type:'about:blank', title, status,
  detail}`), маппинг — в `src/lib/api.ts`. Никаких «голых» строк в теле.
- **Валидация — Zod**, схемы живут в сервисах рядом с логикой.
- **Роли**: VIEWER < MANAGER < ADMIN. Пишущие эндпоинты — минимум MANAGER,
  админские (users/api-keys/audit) — ADMIN. Фронтовый ViewerGuard — только UX;
  настоящая проверка всегда серверная (`withAuth`).
- **Аудит**: любое значимое действие — `logAudit()` (без секретов в details).
- **Идемпотентность**: внешние входы — по ключам дедупа; фоновые задачи —
  claim-стиль; отправки — детерминированный idempotency_key.
- **Секреты**: только `.env` (в git не попадает); в БД — исключительно в виде
  `enc:v1:`; в логах и аудите секретов нет.
- **ПДн (152-ФЗ)**: в репозитории и демо-данных — только синтетика
  (`prisma/seed.ts`); реальные ФИО/телефоны в код и коммиты не попадают.

## 12. Сборка дистрибутива и развёртывание на сервере компании

- Сборка: `bash deploy/build-archive.sh` → четыре артефакта в `download/` +
  `latest.json` (манифест: версия, размер, sha256 каждого):
  1. `trigger-vX.Y.Z.tar.gz` — боевой дистрибутив: standalone-бандл
     Next.js, public, prisma-клиент, скрипты установки. `.env` в архив не
     попадает;
  2. `trigger-vX.Y.Z-src.tar.gz` (~0,8 МБ) — лёгкий исходный архив без
     зависимостей (для разработки; `bun install && bun run build`);
  3. `trigger-repo-vX.Y.Z.bundle` — git-бандл репозитория: ЧИСТЫЙ снапшот
     кода без истории разработки (fresh init + initial commit). Клонирование:
     `git clone <файл>.bundle`; для GitHub — `git remote add origin <URL>` +
     `git push -u origin main`;
  4. `trigger-public-vX.Y.Z.zip` — публичный архив для GitHub: тот же
     чистый снапшот, но zip ВМЕСТЕ с каталогом `.git` («push-ready»):
     распаковать → добавить remote → push; подходит GitHub Desktop
     («Add local repository» → «Publish») — консольный git не нужен.
     Zip, а не tar.gz — Windows распаковывает двойным кликом без 7-Zip.
     Отдельно тот же снапшот умеет собирать `deploy/build-public.sh`
     (без полной сборки `next build`).
  Артефакты 3–4 собираются из rsync-копии дерева БЕЗ истории и внутренних
  материалов (worklog, SPEC, справочники altcraft, вендорские PDF МТС);
  exec-бит нормализуется: исходники 644, исполняемые только `deploy/*.sh`
  (rsync иначе переносит `+x` со всей ФС разработки). Тяжёлые
  tar.gz/бандлы в git не попадают (.gitignore).
- Установка на сервер: `bash deploy/install.sh` (см. `docs/security.md`,
  чек-лист развёртывания: TLS/домен, firewall, права на каталог БД, резервные
  копии). Обновление: `bash deploy/update.sh`.
- Runtime-настройки без пересборки: `FRAME_PROTECTION`, `DATABASE_URL` и др.
  читаются из окружения при старте (`proxy.ts` добавляет заголовки на лету).
- Экспорт/импорт БД — `src/lib/db-backup.ts` / `db-restore.ts` (снапшоты
  атомарны: tmp + rename).
- **Операционные уроки сборки (проверено на практике, v0.4.3)**: при живом
  dev-сервере на машине с 4 ГБ RAM параллельная сборка падает по OOM-киллеру
  (bun ≈1,7 ГБ + dev ≈1,5 ГБ). Рецепт: сборку запускать при остановленном
  dev-сервере и БЛОКИРУЮЩЕ; при нехватке памяти — `bun --smol run build`
  (меньше памяти на JIT-кэш). После rsync-копии исходников в staging ВСЕГДА
  проверять полноту (конфиги `tsconfig.json`/`next.config.ts` терялись —
  134 ошибок «Can't resolve '@/…'»).

- **Инцидент «тестовые данные пропали снова» (29.10, v0.7.0) — два корня**:
  1) dev-сервер умирает по OOM (~2 ГБ RSS после компиляции ~80 роутов +
  браузерных обходов); вместе с ним умирает воркер → снапшоты БД в
  `/home/sync/db-backup` перестают обновляться → при сбросе платформы
  восстанавливается ПРОСТАРЕВШИЙ снапшот. Индикатор: mtime
  `/home/sync/db-backup/custom.db` застыл (воркер мёртв). Лечение:
  перезапустить dev-сервер — первый же тик воркера делает свежий снапшот
  (в логе теперь виден `[db-backup] снапшот БД обновлён` — первое обновление
  после старта логируется).
  2) Холодная верификация standalone-дистрибутива В ПЕСОЧНИЦЕ (где есть
  `/home/sync`) запускает второй воркер, который затирает снапшот/env.backup
  данными тестового экземпляра. ПРАВИЛО: холодные тесты дистрибутива — только
  с `TRIGGER_DB_BACKUP=off TRIGGER_DB_RESTORE=off` в окружении запуска
  (`env -u DATABASE_URL TRIGGER_DB_BACKUP=off TRIGGER_DB_RESTORE=off node …`).
  На сервере компании `/home/sync` нет — обе подсистемы там no-op.

## 13. Производительность и ёмкость (большие базы)

Подробный разбор — `docs/loadtest-report.md` (стенд 4 млн клиентов / 2 млн SMS).
Что нужно знать разработчику из кода:

- **SQLite-прагмы применяются автоматически** при старте (`src/lib/db.ts`,
  единое соединение `connection_limit=1`): `journal_mode=WAL`,
  `synchronous=NORMAL`, `busy_timeout=5000`, `cache_size=64МБ`. Проверить на
  живой БД: `sqlite3 db/custom.db 'PRAGMA journal_mode;'` → `wal`
  (WAL персистентен — хранится в файле БД).
- **Потоковые рассылки**: `executeBroadcastRun` (`services/broadcasts.ts`)
  итерирует сегмент порциями по 1000 строк (курсор `externalId`,
  `iterateSegmentClients`), гвард «не чаще 1 раза в N дней» — один
  батч-запрос на порцию. Ограничение: запуск большой рассылки занимает
  ВЕСЬ тик воркера (минуты) — триггерные SMS в это время не отправляются;
  держать `maxRecipients` ≤10–20 тыс., стратегия multi-tick — §5 отчёта.
- **Дашборд** — SQL-агрегаты `GROUP BY` + покрывающий индекс
  `SmsMessage(createdAt, status, templateName)` (`services/stats.ts`):
  713 мс на 500 тыс. SMS в окне (было 4,9 с — выгрузка в JS).
- **Снапшоты БД — адаптивный интервал** (`db-backup.ts` + `worker.ts`):
  БД ≤1 ГБ — раз в 5 мин, >1 ГБ — раз в 30 мин; переопределение —
  env `TRIGGER_DB_BACKUP_TICKS` (в тиках воркера).
- **Требования к серверу**: 16–32 ГБ RAM (лучше 32 — вся БД в кэше),
  SSD/NVMe. Вердикт по масштабу 4 млн клиентов / 500 тыс. SMS в месяц —
  выдерживает; ограничения (single-writer SQLite, полный скан поиска
  по подстроке, JS-курсор ДР-сегментов) и стратегия роста — §4/§5 отчёта.

## 14. Отладка и диагностика

| Симптом | Где смотреть |
|---|---|
| Сервер/воркер «умер» | `curl localhost:3000/api/health` (db/worker/status), `dev.log` (хвост) |
| Ошибка типа/линта | `bunx tsc --noEmit`, `bun run lint` |
| Событие не запустило воронку | Экран «События» → статус/ошибка; `events_inbox`; логи воркера в `dev.log` |
| Система данных прислала поле вне схемы | Журнал «События» → амбер-алерт «вне схемы» и сводка `/events/unknown-fields`; подключить поле (10.6) / создать кастомное (10.7) или убрать наблюдение |
| SMS не ушло | «SMS-лог» → причина отказа (UNSUBSCRIBED/QUIET_HOURS/…); «Интеграции» → проверка подключения |
| Статус доставки не приходит | «Интеграции» → «Интеграция с системой данных» → карточка «Захват событий» (тумблер/токен); webhook-URL у провайдера; лог `MessageEvent` |
| Пустая БД на новом сервере | Бутстрап при старте (`db-bootstrap.ts`); DDL мог устареть → п. 10.2 |
| Медленные запросы | Prisma-лог `['error','warn']` в `db.ts`; индексы — `schema.prisma`; на больших базах — `docs/loadtest-report.md` |
| Зависла большая рассылка | Запуск занимает тик воркера (см. §13); алерт «тик > 60 с» — рекомендация §5.7 отчёта |

Правило публикации: dev-сервер должен оставаться живым; production-сборку
делать только при остановленном dev (память).
